# 全屏写作：composer 统一发布入口（决策稿）

- 日期：2026-09-20
- 状态：**方案待拍板**。后端前置（文章创建认领附件）已随 `011b27c` 进 main；全屏 UI 未实施。
- 关联：`docs/article-publishing-design.md`（文章功能总设计，§3.3 编写链路为本文档的前置）；`docs/concept-model.md`（两实体一道门）。

---

## 0. 结论摘要

1. **问题**：发布有两个家——发记录在主页 composer，发文章藏在侧栏「文章」→「写文章」。用户想「发表点什么」时被迫先做一次位置判断；文章功能上线后已有真实踩坑（找不到入口）。
2. **定案方向（Kim 09-20 口头拍板）**：**主页 composer 加一个「放大/全屏」按钮。点开放大后，这个发布器就能写文章。** 用户心智只有一条：「发布 = 主页面那个发布组件」，放大是它的自然延伸，不新增第二套入口。
3. **形态**：全屏面板 = 同一个 composer 的展开态。底部操作行加**发布类型选择（记录 / 文章）**，默认「记录」，行为与现有完全一致；选「文章」后发送 = 用当前内容建文章草稿并跳进编辑器（公开发布仍要过编辑器里那道发布门）。
4. **不做的事**：不在小尺寸 composer 里塞长文编辑；不把发布门（slug/描述/公开确认）搬进全屏面板；不做 memo→文章的状态转换门（文章仍是独立实体，composer 只是它的出生地之一）。

## 2. 交互设计

### 2.1 触发：放大按钮

- composer 底栏左侧工具区（# / 图 / 列表 / 语音 一排）的最右加一个 **「全屏写作」图标按钮**（lucide `Maximize2Icon`，8 语言 aria）。
- 点击进入全屏面板；Esc 或右上「收起」（`Minimize2Icon`）返回，**草稿不丢**（同一份 `MemoCaptureInput`，只是换了容器）。
- 全屏面板用 Base UI Dialog 全屏 popup（现有 `ui/dialog.tsx` 已接 glass 材质，直接复用；`p-0` 自定义内容）。

### 2.2 全屏面板内容

从上到下：

1. **标题输入框**——仅「文章」类型显示（记录无标题，这是概念模型定死的）。留空合法，发布时才要求非空。
2. **编辑器**——类型决定扩展集：记录=现有 composer 扩展；文章=`buildArticleExtensions`（H1–H4 / 表格 / 高亮代码块）。切换类型时**保留正文文本**：markdown 是唯一事实源，切换只换编辑器容器与工具栏（TipTap 两个实例各自挂载，内容经 markdown 字符串交接，已有 `composer-roundtrip` 幂等测试背书）。
3. **底部操作行**——与现有 composer 同构，左侧工具栏随类型切换，右侧：
   - **类型 chip**（dropdown，样式对齐现有「个人/团队」chip）：「记录 · 发到时间线」/「文章 · 公开可收录」。默认「记录」。**选「文章」时隐藏「个人/团队」chip**——文章是公开发布面，团队可见性对它不成立（团队文章是 P2），一个面板里不能有两个打架的范围选择。
   - **主按钮**随类型变：记录=圆形发送钮（现状）；文章=「继续编辑」主钮。
4. 语音速记、# 标签补全、`[[` wikilink 补全、图片粘贴拖拽：全屏内全部保持可用（同一 controller）。

### 2.3 两条提交路径

| 类型 | 动作 | 走的链路 |
|---|---|---|
| 记录 | 发送钮 | 现有 `handleCaptureSubmit` → `createMemoWithAttachments`（乐观插入、离线队列、草稿持久化**全部不动**） |
| 文章 | 「继续编辑」钮 | `createArticleWithAttachments`（已落地）：文件逐个上传 → 内容+附件 markdown 拼接 → `POST /api/app/articles`（带 `attachment_names` 认领）→ 跳 `/articles/<uuid>/edit`；composer 清空 |

- 文章路径**不做乐观插入、不走离线队列**：文章草稿有服务端行 + 编辑器自动保存兜底，失败就地 toast 报错、草稿留在全屏面板里可重试。
- 空内容也允许进文章路径（建空草稿进编辑器），与列表页「写文章」行为一致。
- 内容超 200KB（文章上限）：文章路径提交前拦截 toast；记录路径维持现有 100KB 校验不动。

### 2.4 图片与附件接线（已落地的部分）

- composer 里粘贴/选文件的图是**预上传不绑定**的，孤儿 GC 7 天会收。记忆型 memo 靠发送后 `bindMemoAttachments` 认领；文章靠 `createArticle` 的 `attachment_names` 在**同一请求**里认领（`011b27c`，域层先预检再建文，坏 id 不留半成品行）。
- 拼接规则：正文 → 每个附件一段（图=内联 `![]()`；非图=文件链接 `[]()`，避免 PDF 渲染成破图）。未在正文引用的附件仍会被认领——公开页有「未引用附件」画廊兜底，不会丢。

## 3. 为什么这是对的心智（记录）

- **一个发布组件**：用户永远只知道「在主页那个框里写」，放大是同一框的自然延伸，没有第二个入口要找。
- **类型是路由不是发布**：选「文章」不公开任何东西，只是决定内容去哪、用哪套编辑器；公开发布仍要过编辑器的发布对话框（含公开确认）。风险面没有变大。
- **放大即长文**：写文章的意图通常发生在正在打字的时候；全屏给了长文该有的空间（标题、工具栏、大画布），小框里永远不该写长文。
- **与概念模型一致**：记录/任务两实体之外，文章是「从记录里长出的发表形态」；composer 成为它的出生地，正好把这句话变成操作路径。

## 5. 验收标准

```
1. 点放大钮进全屏；Esc/收起钮退出；草稿在进出间不丢（含已贴图片）
2. 默认「记录」：发送行为与旧 composer 逐字节一致（乐观插入/离线队列不回归）
3. 选「文章」：发送建草稿跳编辑器；图片随之认领（D1 attachments.articleId 非 null）
4. 文章路径不触发乐观插入；失败 toast 且草稿保留
5. 类型切换保留正文；记录→文章后标题框出现且为空
6. 选文章时「个人/团队」chip 隐藏；切回记录恢复且保持原可见性偏好
7. 小尺寸 composer 无类型 chip——分流只存在于全屏态
8. 8 语言 parity 测试绿
```

## 6. 边界与明确不做

- 不把长文编辑内联进小尺寸 composer（拖重核心快路径）。
- 不把发布对话框（slug/SEO/公开确认）搬进全屏面板——发布门留在编辑器，全屏只负责「内容长在哪」。
- 不做文章→记录的反向门、不做团队文章（P2）、不在全屏面板显示回收站/已发布列表（那是侧栏管理面的事）。
- Memos 兼容 API / MCP 不暴露类型选择（文章不进 `/api/v1` 契约，既定边界）。
